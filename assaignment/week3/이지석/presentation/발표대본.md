# 3주차 발표 대본 — 이지석

권장 발표 시간: 8~10분. HTML을 내려받아 브라우저로 열고 방향키로 이동합니다. N은 대본, F는 전체화면입니다. 화면 공유 중 대본을 켜면 청중에게도 보이므로 리허설용으로 사용하세요.

## 1. Kubernetes 배포와 CI/CD·GitOps

오늘은 같은 Nginx를 세 가지 도구로 배포한 결과를 비교하고, 소스 변경이 실제 Pod와 응답까지 연결되는 과정을 설명하겠습니다. 실습은 3노드 kind에서 진행했습니다. 성공한 검증과 아직 남은 GHCR 공개 설정을 구분해서 말씀드리겠습니다.

## 2. 이번 실습에서 확인한 범위

배포 비교, 직접 CI, GitOps의 실제 응답까지 확인했습니다. 다만 GHCR 패키지는 현재 Private입니다. 검증 동안만 유효한 Actions job 토큰으로 pull했습니다. 따라서 전체 과제의 완료 상태를 100%라고 말하지 않습니다. 공개 이미지 요건을 충족하려면 Public 전환 후 새 배포를 다시 확인해야 합니다.

## 3. YAML·Kustomize·Helm 비교

일반 YAML은 최종 설정을 직접 읽기 쉽지만 환경별 중복이 생기기 쉽습니다. Kustomize는 일반 YAML을 유지하며 변경분만 overlay로 관리합니다. Helm은 values로 템플릿을 렌더링하고 릴리스 단위로 관리합니다. 우리 팀 앱의 환경 차이는 Kustomize, 여러 사용자에게 배포하는 패키지는 Helm이 적합하다고 판단했습니다. 출처: https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/ 및 https://helm.sh/docs/chart_template_guide/getting_started/

## 4. 최종 리소스의 spec은 동일

세 도구의 기본 설정을 맞춘 뒤 렌더링된 Deployment와 Service의 spec을 비교했습니다. 이름과 포트, 이미지가 같고 namespace는 배포할 때 주입합니다. Kustomize prod는 replicas가 2로 바뀌고 실제로 2개 Pod Ready까지 확인했습니다. Helm은 image와 replicaCount override도 검증했습니다. namespace나 metadata 차이와 애플리케이션 동작을 바꾸는 spec 차이를 구분하는 것이 핵심입니다.

## 5. replicas 변경과 이미지 변경

실제 실험에서 replicas만 바꾸면 기존 ReplicaSet 이름이 유지됐습니다. 이미지 참조를 바꾸자 새로운 ReplicaSet이 생기고 이전 ReplicaSet의 desired는 0이 됐습니다. 도구가 무엇인지는 controller가 판단할 조건이 아닙니다. Deployment의 Pod template이 달라졌는지가 새 rollout과 연결됩니다. 출처: https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#updating-a-deployment

## 6. Actions가 직접 배포하는 경로

GitHub-hosted runner는 노트북의 로컬 kind API에 기본적으로 접근할 수 없습니다. 그래서 빌드는 GitHub-hosted에서, 배포는 클러스터에 접근할 수 있는 개인 runner에서 실행했습니다. build.outputs.image를 넘겨 같은 실행이 만든 이미지가 배포되도록 했습니다. API를 인터넷에 공개하지 않았고 외부 PR 코드를 개인 runner에서 실행하지 않습니다. 이번 검증은 Private GHCR 때문에 deploy job의 임시 읽기 토큰을 추가했습니다.

## 7. v1과 v2의 실제 변경

v1 배포를 확인한 다음 소스의 version 응답을 v2로 바꿨습니다. 직접 kubectl 이미지 변경이나 수동 배포 없이 workflow가 전체 SHA 태그를 바꿨고 새 Pod가 v2를 응답했습니다. Actions 성공만으로 배포를 증명한 것이 아니라 Deployment image, Pod image와 imageID, 실제 응답까지 연결했습니다. SHA 태그는 소스 이력이고 digest는 이미지 내용 식별자입니다.

## 8. Argo CD가 Git의 상태를 적용

최종 CI에서는 self-hosted 배포 job을 제거하고 Git을 갱신하는 job으로 바꿨습니다. Argo CD가 Git을 읽고 적용하므로 CI의 build/update-manifest에는 kubeconfig가 없습니다. 단, 이번 검증에서는 비공개 이미지의 임시 인증을 유지하기 위한 별도 보조 job만 클러스터에 접근했습니다. 소스 SHA A와 manifest commit B는 역할이 다르므로 값이 서로 다릅니다. 이미지 게시만으로 Git의 image가 바뀌지는 않습니다.

## 9. v3 자동 GitOps 배포 결과

v3 소스 commit으로 빌드와 update-manifest job이 성공했습니다. 봇이 만든 설정 commit B를 Argo CD가 polling해서 동기화했고 실제 응답이 v3로 바뀌었습니다. Git 변경 직후 즉시 화면이 바뀌지는 않았습니다. controller가 Git을 다시 읽는 간격이 있으므로 실행 타임라인과 최종 응답을 함께 봤습니다. 보고서에 두 전체 SHA와 Actions 링크가 있습니다.

## 10. 드리프트와 selfHeal

Git commit은 고정한 채 selfHeal만 바꿨습니다. selfHeal을 끈 상태에서는 live replicas 3이 유지됐고 켜자 1로 복원됐습니다. 다시 3으로 바꿔도 복원됐습니다. 또 초기 이미지 인증 실패 때에는 Synced인데 Progressing이고 Pod는 ImagePullBackOff였습니다. 선언을 적용했다는 사실만으로 앱 정상 동작을 판단할 수 없습니다. 출처: https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/

## 11. 남은 조건: GHCR Public 전환

이 제한은 숨기지 않고 과제 맨 앞과 발표에도 표시했습니다. 기존 Pod가 실행 중이어도 새 노드에서 이미지를 다시 받을 수 있다는 보장은 없습니다. 공개 전환 전에는 지속 배포가 완성됐다고 설명하지 않겠습니다. Git 읽기용 read-only deploy key는 계속 유효하지만 이미지 pull 인증과는 별개입니다. 출처: https://docs.github.com/en/actions/concepts/security/github_token

## 12. 발표 후 확인할 질문

마지막으로 세 질문을 정리합니다. GitOps는 Git의 선언을 실제 상태에 맞추는 반복 과정입니다. 복구 역시 Git에서 해야 이후 reconciliation과 충돌하지 않습니다. 데모는 보고서의 캡처와 추적표를 먼저 보여 주고, Public 전환이 완료된 경우에만 라이브 새 배포를 시연하겠습니다. 이 발표는 3주차 범위만 다뤘습니다.

## 예상 질문과 짧은 답변

- **왜 latest를 안 썼나요?** 같은 태그를 덮어쓰면 소스와 배포를 연결하기 어렵습니다. 전체 소스 SHA로 구분하고 imageID도 확인했습니다.
- **SHA 태그는 불변인가요?** 태그는 덮어쓸 수 있습니다. 내용 고정은 digest 참조가 더 직접적입니다.
- **index digest와 imageID가 다르면 오류인가요?** 멀티 플랫폼 index는 아키텍처별 manifest를 참조합니다. 서로 다른 단계의 digest를 단순 문자열 비교하면 잘못 판단할 수 있습니다.
- **Git repo가 Private인데 이미지는 Public일 수 있나요?** 가능합니다. 저장소와 패키지 공개 범위는 별도입니다. 이번 패키지는 아직 Private이라 Public 전환이 남았습니다.
- **왜 개인 runner가 필요한가요?** 직접 배포 단계에서 로컬 kind API에 접근해야 하기 때문입니다. 최종 GitOps build/update-manifest는 GitHub-hosted에서 실행합니다.
- **CI가 클러스터에 정말 접근하지 않나요?** 최종 앱 CI는 접근하지 않습니다. 이번 Private 이미지 검증 보조 job만 임시 imagePullSecret 설정을 위해 접근했습니다. Public으로 바꾸면 이 보조 job이 필요 없습니다.
- **GitHub Actions 봇 commit은 내 계정 제출 조건과 충돌하나요?** 저장소·원본 소스 commit·공용 제출 PR은 dev-jiseok이며 자동 생성한 설정 commit만 github-actions[bot]입니다.
- **selfHeal과 자동 Sync는 같은 기능인가요?** 자동 Sync는 Git의 새 원하는 상태를 반영하고, selfHeal은 Git revision이 같아도 live drift를 복구하도록 합니다.
- **prune은 해봤나요?** 최종 설정은 켰지만 리소스 삭제 실험은 수행하지 않았습니다. 이론과 실측 범위를 구분합니다.
- **실패 이미지 롤백은 해봤나요?** 존재하지 않는 태그로 바꾸는 선택 심화는 하지 않았습니다. 실제로 관찰한 장애는 초기 인증 순서로 발생한 ImagePullBackOff입니다.
- **지금 발표 중 새 버전을 배포해도 되나요?** Public 전환과 익명 pull 확인 후 가능합니다. 그 전에는 저장된 실측으로 발표하고 제약을 명시합니다.

## 시연 순서

1. 공용 PR의 도구 비교 캡처와 v1/v2 추적 기록을 보여 줍니다.
2. v3의 소스 SHA A와 설정 SHA B를 가리키며 역할 차이를 설명합니다.
3. selfHeal 꺼짐/켜짐 표와 Synced/Healthy의 차이를 설명합니다.
4. Public 전환이 끝났을 때만 RUNBOOK의 port-forward와 curl로 라이브 확인합니다.

## 발표에서 피할 표현

- “완전히 끝났습니다”: Public 이미지 요건이 남아 있습니다.
- “캡처는 Argo CD UI입니다”: 제출 PNG는 실제 수집한 출력·JSON을 렌더링한 기록입니다.
- “세 도구가 Kubernetes를 서로 다르게 동작시킵니다”: 최종 spec과 controller가 동작을 결정합니다.
- “GitOps면 이미지 업로드만 하면 됩니다”: Git의 image 참조 갱신이 필요합니다.
